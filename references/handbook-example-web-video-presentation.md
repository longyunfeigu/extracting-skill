# Handbook Example: `web-video-presentation`

This is a style sample for `references/HANDBOOK-FORMAT.md`. It is not a full
handbook. Use it to calibrate voice, stage shape, concept explanation, and the
first-person AI working path.

## 先感受一下

这个 skill 看起来 cool 的地方不是"会写 React"。真正厉害的是：我拿到一篇
文章以后，不能直接冲去写网页。skill 先让我把文章变成能念出来的
`script.md`，再变成可开发的 `outline.md`，然后让我在最便宜的返工点和
用户一次对齐稿子、计划、主题、素材和开发模式。只有这些都对齐后，我才
开始写网页、音频和录屏流程。

普通 AI 很容易把"文章做成视频"理解成"把文章拆成几页 PPT"。这个 skill
防的就是这件事：它把视频生产拆成几个不会互相污染的阶段，让我每一步都
知道自己现在该决定什么、不该提前决定什么。

## 一个小例子

**用户输入：**

```text
我有一篇文章，讲 GPT Image 新模型的文字渲染能力。
帮我做成一个 3 分钟 B 站风格视频网页。
```

## 高层地图

```text
用户意图
  把一篇文章做成可录屏的视频网页
      │
      ▼
我作为 AI 的总任务
  把"读的内容"变成"听 + 看 + 点击推进"的 16:9 网页视频
      │
      ▼
阶段拆分
  内容编写 → 用户对齐 → 网页开发 → 音频合成 → 录屏
      │
      ▼
关键产物
  article.md → script.md → outline.md → Chapter.tsx + narrations.ts → mp3
```

## 概念先解释

### `script.md`

**人话解释：** 它是给视频用的口播节拍稿。它不是摘要，而是观众最后会听到
的那条线。

**它出现在哪个场景：** 用户给我的是书面文章。文章适合读，不适合直接念。
我必须先把它改成能自然说出口的稿子。

**它解决什么问题：** 防止我把书面文章直接搬到视频里，导致观众听起来像在
听论文摘要。

**我作为 AI 怎么用它：** 我按 `references/SCRIPT-STYLE.md` 改写原文，用
`---` 切出一个个完整想法。后面的章节、step、口播音频都会受到它影响。

**容易误解：** 它不是短摘要。这个 skill 明确要求保留足够信息，不能为了
口语化把事实、数字、案例、论证链剪没。

### `outline.md`

**人话解释：** 它是网页开发计划，告诉后面的章节开发"这一章讲什么、每一步
屏幕上有什么、有哪些原文细节可以挂到画面里"。

**它出现在哪个场景：** `script.md` 生成后，我已经知道视频怎么说，但还不
知道网页怎么分章、每章几步、每一步放什么画面重点。

**它解决什么问题：** 防止章节开发阶段一边想内容、一边想结构、一边想素材，
最后节奏混乱。

**容易误解：** 它不是视觉规划。它不应该写具体动画、CSS 手段、毫秒级时长。
这些判断要留到章节实现阶段。

### 信息池

**人话解释：** 每章从原文章里抽出来的一小包细节：数字、引用、案例、时间、
对比、出处。

**它出现在哪个场景：** 我写 `outline.md` 时，每章开头都要放信息池。

**它解决什么问题：** 防止网页画面只是把口播稿打在屏幕上。口播负责讲清楚，
画面要比口播多挂一点细节，视频才有信息密度。

## AI 运行轨迹

### 1. 我先判断用户给了什么

我现在拿到的是一篇文章和一个目标："做成 3 分钟 B 站风格视频网页"。

skill 先让我判断输入类型。用户给的是原始文章，不是现成口播稿，也不是空
主题。所以我进入内容编写阶段。

我不能直接写网页。因为文章是给人读的，网页视频是给人听和看的。直接写网页
会把文章变成几页大字 PPT。

我产出下一步需要的工作判断：先生成 `script.md` 和 `outline.md`。

这里能偷的招：先把用户输入分流成明确路径，不要让一个 skill 用同一套动作
处理所有入口。

### 2. 我生成 `script.md`

我现在拿到的是 `article.md`。skill 要我先读 `references/SCRIPT-STYLE.md`。

这个文件约束我怎么把书面文章改成能念出来的稿子。它最重要的底线不是
"口语化"，而是"信息不能被我剪掉太多"。如果原文有数字、案例、论证链，我
可以换说法，但不能当成累赘删掉。

坏场景是这样的：我为了显得口语化，把文章压成几句漂亮总结。观众听起来轻松，
但原文真正的信息都没了。

所以我生成 `script.md` 时要同时满足两件事：能说出口，信息还在。

这个产物下一步喂给 `outline.md`。`script.md` 里的 `---` 会变成后面切 step
的重要依据。

这里能偷的招：先把原始材料转成执行格式，再让后续阶段吃这个格式。

### 3. 我保留 `article.md`，因为画面还需要原文细节

我已经有 `script.md` 了，但 skill 不让我删掉原文。

原因很简单：`script.md` 管节奏，`article.md` 管画面密度。口播稿为了好听，
会压缩很多细节；但网页画面需要数字、引用、案例、角标、小字、对比图。这些
东西不能靠我现编，必须回原文找。

```text
article.md
  ├── 改写成能念的稿子 ──► script.md      管节奏
  └── 抽取画面细节 ─────► 信息池          管画面密度
```

这里能偷的招：当两个后续阶段需要不同信息时，不要让一个中间文件吞掉全部
职责。保留两个源，各管一类决策。

### 4. 我生成 `outline.md`，但故意不写动画

我现在有 `script.md` 和 `article.md`。skill 要我读
`references/OUTLINE-FORMAT.md`，把视频切成章节和 step，并给每章抽信息池。

我不能在 outline 里写"这里 blur clear，那里 wipe，第三步 spring"。

看起来这有点保守。既然已经规划网页，为什么不顺手把动画也写了？

坏场景是：我在信息还不够时提前写死动画，后面的章节开发只能照着翻译。
那样 chapter agent 就不再根据内容关系做设计，只是在执行上游的猜测。

所以 outline 只写三件事：

- 这章讲什么
- 每一步屏幕上有什么
- 有哪些原文细节可以挂到画面里

真正的视觉动作留到章节实现阶段，由 `CHAPTER-CRAFT.md` 约束。

这里能偷的招：上游只做自己有足够信息的决定，把需要现场判断的事留给下游。

### 5. 我停在 Checkpoint Plan

我已经写完 `script.md` 和 `outline.md`。这时候我很容易犯一个错：觉得计划
都好了，可以开始写 React 了。

skill 不允许我这么做。

因为现在所有东西还都是文本：稿子不对，改 `script.md`；章节切错，改
`outline.md`；主题不合适，换 theme；素材缺失，先让用户补或用 placeholder；
开发方式不确定，先选逐章、顺序还是并行。这些现在改都便宜。

一旦我开始写章节代码、动画、CSS 和音频，任何方向错了，返工都会变重。

所以 skill 把我拦在这里，一次让用户确认 5 件事：

1. 稿子
2. outline
3. 主题
4. 素材
5. 开发模式

这里能偷的招：在昂贵工作开始前，设置一次多项对齐 checkpoint。

### 6. 我先做第 1 章，因为它是风格锚点

用户确认后，我可以脚手架项目。但我仍然不能把所有章节并行扔出去。

skill 要我先用主线程完整做第 1 章，并让用户验收。

第 1 章不是普通章节。它是这次项目的样板间：主题是否合适、字号是否舒服、
动画是否有视频感、`CHAPTER-CRAFT.md` 有没有盲区，都会在第 1 章暴露。

如果这时候用户说"气质不对"，我只改一章。如果等全部章节写完再发现，成本
就高很多。

这里能偷的招：先做透一个真实样本，用它校准风格和规则，再放开后续批量工作。

### 7. 我每章都读 `CHAPTER-CRAFT.md`

到了单章开发，我的任务不再是"把 outline 翻译成页面"。skill 要我每章都读
`references/CHAPTER-CRAFT.md`。

这个文件在防一个很具体的坏结果：我把视频网页写成 PPT。

它规定每章必须有视觉演示，不能整章纯文字；清单要逐个揭示，不能一次全展示；
画面要回 `article.md` 抽细节，不能只复述口播稿；颜色和字体要走主题 token，
不能写死；缺素材要承认缺，不能编假数据或拿 emoji 凑。

这里能偷的招：不要只说"做得有视频感"，要把审美要求写成验收不过的失败条件。

### 8. 我把 `narrations.ts` 当成最终真相源

每章实现时，我还必须写 `narrations.ts`。

这个文件存每个 step 对应的口播文本。它的数组长度必须等于章节代码里的 step
数量。否则自动播放和音频会错位。

```text
Chapter.tsx
  step 0 / step 1 / step 2
        │ 必须一一对应
        ▼
narrations.ts
  [口播0, 口播1, 口播2]
        │
        ▼
audio-segments.json → mp3 → ?auto=1 自动录屏
```

这里的设计很关键：早期 `script.md` 决定节拍，`outline.md` 规划步骤，但到了
真实网页和音频阶段，离运行时最近的 `narrations.ts` 才是最终真相源。

这里能偷的招：当多个文件都会漂时，让离运行时最近的文件当最终真相源，其它
文件对齐它。

## 关键设计选择

### outline 不写动画

**看起来多此一举的地方：** 为什么不一次把动画也规划好？

**坏场景：** 我在章节还没实现、主题和素材还没真正落地时提前写死动画，后面
只能机械执行，视频变成 PPT 动效堆叠。

**skill 怎么约束我：** `outline.md` 只写节奏、屏幕内容和信息池，不写 CSS、
动画名、毫秒级时长。

**解决的问题：** 把视觉判断留给真正掌握章节上下文的阶段。

**可偷的招：** 不让上游抢下游判断权。

### 自检后先修复，再汇报

**看起来多此一举的地方：** 自检结论已经知道了，为什么不能先告诉用户？

**坏场景：** 我把 reviewer 或自检发现的问题原样汇报给用户，却没有修。用户
以为我在交付，其实只是转述问题。

**skill 怎么约束我：** 每个关键产物完成后，必须自检、修复，再汇报。

**解决的问题：** 把质量检查变成闭环，而不是报告装饰。

**可偷的招：** 检查项必须接修复动作，否则只是仪式。

## 能偷的招

### 双源分工 · 状态：候选

**它防什么坏结果：** 一个中间文件吞掉全部职责，导致后续阶段既缺节奏又缺
细节。

**场景例子：** `script.md` 管口播节奏，`article.md` 继续管画面细节。

**怎么复用：** 当源材料要同时服务两个不同维度时，保留两个源，并明确每个源
管什么。

**反例：** 简单备份原文但后续从不读取，不是这招。

**代价：** 后续阶段要记得读两个源，文档必须把边界写清楚。

### 便宜返工点 checkpoint · 状态：候选

**它防什么坏结果：** AI 过早进入昂贵实现，最后在代码、动画、音频都完成后
才发现方向错了。

**场景例子：** `script.md` + `outline.md` 完成后必须停在 Checkpoint Plan。

**怎么复用：** 在从文本计划进入工程实现、批量生成、外部 API 调用之前，设置
一次必须暂停的对齐点。

**反例：** 每做一点都问用户，不是这招；那会让流程变慢。

**代价：** 多一次用户确认，但换来更低的返工风险。

### 运行时真相源 · 状态：候选

**它防什么坏结果：** 多个文件各自声明 step 数、口播和音频，最后自动播放错位。

**场景例子：** `narrations.ts` 同时决定 step 数和音频合成文本。

**怎么复用：** 当计划文件和运行文件可能漂移时，指定离运行最近的一份为最终
真相源。

**反例：** 把最早的规划文档永远当真，不是这招；真实实现会变。

**代价：** 每次实现变更后，需要同步上游计划或说明哪里允许漂。
